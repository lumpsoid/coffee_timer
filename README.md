# Coffee Timer

Coffee Timer runs multi-step coffee brewing recipes. Each step counts down on
its own; at every step boundary the phone vibrates and plays a sound, and the
screen stays awake while a brew runs. Recipes and settings are stored locally
in SQLite.

The app is a **Rust core** driven through [rinf](https://github.com/cunarist/rinf)
by a **Flutter GUI**. Rust owns every rule and all state. Flutter renders the
state Rust sends, forwards user intents, and performs platform effects (sound,
vibration, wakelock) when told to. It holds no business logic.

## Architecture

```
native/core   coffee_timer_core   rules + state: feature controllers. No rinf, no async, no I/O.
      ▲
native/store  coffee_timer_store  SQLite persistence, migrations, UUID v7 ids.
      ▲               ▲
native/hub    hub     native/cli  coffee_timer_cli
  rinf bridge           command-line head, same controllers
      ▲
lib/src/bindings      Dart signal classes, generated by `rinf gen` (gitignored)
      ▲
lib/                  Flutter GUI: holders, pages, widgets, effect performer
```

Dependencies point down the arrows only.

- **Feature controllers** in core each own one state object:
  `RecipeCatalog` (shared), `SettingsController`, `BrewController`,
  `EditorController`. An action takes plain values, updates the state, and
  returns only what state can't hold: platform `Effect`s or a
  `CatalogChange`.
- **Infrastructure** (store, id generator) enters a controller through its
  constructor as `Box<dyn Trait>`; the traits live in core, the real
  implementations in `store`, fakes in core behind the `test-fakes` feature.
  The shared `RecipeCatalog` is passed into actions as `&` / `&mut`.
- **The hub** is one tokio task that owns every controller. It turns Dart
  signals into controller actions and sends each feature's whole view state
  back (diffs for the recipe list). It holds no business `if`.
- **The CLI** is a second head on the same core and store. It proves the core
  doesn't need Flutter.
- **Flutter** keeps one view-state holder per feature, replaced from Rust
  signals, and one listener that performs `PlatformEffect`s.

## Getting started

### Prerequisites

- [Flutter SDK](https://docs.flutter.dev/get-started/install) (Dart `^3.9.2`)
  with the toolchain for your target (Android SDK, Xcode, or a desktop
  target). Check with `flutter doctor`.
- [Rust](https://www.rust-lang.org/tools/install), stable 1.91 or newer.
- The rinf CLI, matching the `rinf` crate version in
  [`native/hub/Cargo.toml`](native/hub/Cargo.toml):

  ```shell
  cargo install rinf_cli
  ```

### First run

```shell
git clone <repo-url> coffee_timer && cd coffee_timer
flutter pub get
rinf gen          # generates lib/src/bindings; required before any flutter command
cargo test        # core, store, cli and hub tests
flutter test
flutter run
```

The Dart bindings are gitignored, so run `rinf gen` on every fresh checkout
and after any change under `native/hub/src/signals/`. `rinf gen --watch` is
broken; run it by hand. The app keeps its database at
`<app documents>/coffee_timer.db`, seeded with Espresso and Pour Over on
first launch.

### Try the core without Flutter

```shell
cargo run -p coffee_timer_cli -- --db /tmp/ct.db list
cargo run -p coffee_timer_cli -- --db /tmp/ct.db brew pourover-uuid --fast
cargo run -p coffee_timer_cli -- --help
```

`brew --fast` prints every tick, step status and effect without waiting in
real time. More commands are in [docs/README.md](docs/README.md#cli).

## Working on the code

### Gates

Run all four before committing:

```shell
cargo clippy --all-targets -- -D warnings
cargo test
flutter analyze
flutter test
```

The workspace denies `unwrap_used`, `expect_used`, `panic` and
`wildcard_imports`: return `Result` instead of panicking.

### Where a change goes

Most changes follow the same path down and back up the layers:

1. **Rule or state** → a controller or model type in
   [`native/core`](native/core). Test it there with `cargo test`: run an
   action, assert the state. No Flutter needed.
2. **Persistence** → [`native/store`](native/store); schema changes are a new
   entry in its migrations, never an edit to an old one.
3. **New data for the GUI** → a signal in
   [`native/hub/src/signals`](native/hub/src/signals) plus a pure mapping in
   the feature's `native/hub/src/<feature>.rs`; then `rinf gen`.
4. **New user intent** → a `DartSignal` with exactly one receiver, as one arm
   of the loop in [`native/hub/src/run.rs`](native/hub/src/run.rs).
5. **Display** → the feature's holder in [`lib/holders`](lib/holders) and its
   page in [`lib/pages`](lib/pages). Dart only renders and forwards; if a
   widget needs to decide something, that decision belongs in core.

Behaviour carried over from the legacy app is deliberate, and the bugs fixed
during the port are listed in [docs/port-plan.md](docs/port-plan.md); don't
reintroduce them.
